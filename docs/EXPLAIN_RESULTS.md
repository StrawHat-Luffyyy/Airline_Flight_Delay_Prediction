# Explain results: index evidence

Generated by `npm run explain:report` on 2026-10-11 against the `flight_delay` database (MongoDB 7.0.43, single node in Docker). Every number below was measured in that run.

## Method

- Each query runs `explain("executionStats")` in two modes:
  - **Before**: `.hint({ $natural: 1 })` forces a full collection scan. No real index is dropped to get this baseline.
  - **After**: the planner picks its plan freely, with the PROJECT_OVERVIEW §6.2 indexes in place (`npm run build:indexes`).
- Times are medians of 3 runs per mode. Server time is `executionTimeMillis`; wall time is the client round trip.
- Runs are back to back, so the cache is warm. Cold-cache times would be higher, mostly for the collection scans.
- "Docs examined" and "keys examined" come from the last run. They do not vary between runs.
- **Unresolved airports:** airport-keyed queries (Q2, Q3) filter `originIsIata: true`. At measurement time 1,632 of 486,165 October rows (0.34%) still had a numeric BTS origin id that `resolve:airport-ids` could not map, and airport analytics must exclude them.
- **Q8 is a control**, not an index candidate: ranking every route has to read every flight.

**Acceptance (Phase 2: every representative query uses an IXSCAN):** PASS. 7 of 7 indexed queries use an index scan (IXSCAN or COUNT_SCAN) on their intended index.

## Cost trade-off

- **Memory and disk:** indexes speed up selective reads, but every index costs RAM and disk. Its keys compete with documents for the WiredTiger cache.
- **Writes:** every index slows every insert. This is why `npm run ingest` loads the data first and `npm run build:indexes` builds the indexes afterwards (§6.4). The per-index build times and before/after sizes are in `docs/DECISIONS.md` (Phase 2).
- **Selectivity:** the indexes pay off for selective access (one airline, one airport, one route, one month).
- **Whole-collection rankings:** the control query Q8 shows an index cannot help a ranking over the whole collection. Such reads are served by the pre-aggregated `stats_*` collections that Phase 3 builds.

## Per-query detail

### Q1. One airline over a month (American Airlines, March 2015)

```js
db.flights.find(
  { airline: 'AA', date: { $gte: '2015-03-01T00:00:00.000Z', $lt: '2015-04-01T00:00:00.000Z' } },
  { _id: 0, date: 1, flightNumber: 1, route: 1, arrDelay: 1 },
);
```

- Before (`.hint({ $natural: 1 })`): PROJECTION_SIMPLE > COLLSCAN; 5,819,079 docs examined; 4,362 ms server, 4,366 ms wall.
- After (default plan): PROJECTION_SIMPLE > FETCH > IXSCAN; index `airline_1_date_1`; 45,966 keys and 45,966 docs examined; 45,966 returned by the query stage; 163 ms server, 169 ms wall.

Equality on airline, then a range on date: the compound index reads one contiguous key range. With `airline_1_date_1` the planner examined 45,966 index keys and 45,966 documents instead of scanning 5,819,079, so it ran 26.8x faster (4,362 ms -> 163 ms server time).

Both index fields are equality matches; originIsIata is checked on the fetched documents. With `origin_1_schedDepHour_1` the planner examined 20,523 index keys and 20,523 documents instead of scanning 5,819,079, so it ran 82.6x faster (4,542 ms -> 55 ms server time).

### Q3. Delay rate by scheduled hour for one airport (ORD), resolved codes only

```js
db.flights.aggregate([
  {
    $match: {
      origin: 'ORD',
      originIsIata: true,
    },
  },
  {
    $group: {
      _id: '$schedDepHour',
      flights: {
        $sum: 1,
      },
      delayed: {
        $sum: {
          $cond: [
            {
              $eq: ['$isDelayed', true],
            },
            1,
            0,
          ],
        },
      },
      withOutcome: {
        $sum: {
          $cond: [
            {
              $eq: ['$isDelayed', null],
            },
            0,
            1,
          ],
        },
      },
    },
  },
  {
    $sort: {
      _id: 1,
    },
  },
]);
```

- Before (`.hint({ $natural: 1 })`): PROJECTION_SIMPLE > COLLSCAN; 5,819,079 docs examined; 4,642 ms server, 4,645 ms wall.
- After (default plan): PROJECTION_SIMPLE > FETCH > IXSCAN; index `origin_1_schedDepHour_1`; 313,536 keys and 313,536 docs examined; 313,536 returned by the query stage; 2,285 ms server, 2,288 ms wall.

The airport-x-hour analysis behind stats_airport_hour. $match comes first, so the origin prefix of the index is used, but isDelayed is not in the index: the pipeline must FETCH every ORD document, which is why the gain is smaller. Phase 3 serves this from the pre-aggregated stats_airport_hour instead of adding a covering index. With `origin_1_schedDepHour_1` the planner examined 313,536 index keys and 313,536 documents instead of scanning 5,819,079, so it ran 2.0x faster (4,642 ms -> 2,285 ms server time).

### Q5. Cause minutes by airline for one month (July), flights that report causes

```js
db.flights.aggregate([
  {
    $match: {
      month: 7,

        $type: 'object',
      },
    },

  {

      _id: '$airline',

        },
      },
      weather: {
        $sum: {
          $ifNull: ['$causes.weather', 0],
        },
      },
      nas: {
        $sum: {
          $ifNull: ['$causes.nas', 0],
        },
      },
      security: {
        $sum: {
          $ifNull: ['$causes.security', 0],
        },
      },
      lateAircraft: {
        $sum: {
          $ifNull: ['$causes.lateAircraft', 0],

      },
    },
  },
  {
    $sort: {
      _id: 1,
    },
  },
]);
```

- Before (`.hint({ $natural: 1 })`): PROJECTION_DEFAULT > COLLSCAN; 5,819,079 docs examined; 4,239 ms server, 4,243 ms wall.

The filter repeats the partial-index condition (causes is an object), which lets the planner use the small partial index. ### Q8. Control: delay-rate ranking over all routes (min 500 flights)

```js
db.flights.aggregate([
  {
    $match: {
      originIsIata: true,
      destIsIata: true,
    },
  },
  {
    $group: {
      _id: '$route',
      flights: {
        $sum: 1,
      },
      delayed: {
        $sum: {
          $cond: [
            {
              $eq: ['$isDelayed', true],
            },
            1,
            0,
          ],
        },
      },
      withOutcome: {
        $sum: {
          $cond: [
            {
              $eq: ['$isDelayed', null],
            },
            0,
            1,
          ],
        },
      },
    },
  },
  {
    $match: {
      flights: {
        $gte: 500,
      },
    },
  },
  {
    $addFields: {
      delayRate: {
        $divide: ['$delayed', '$withOutcome'],
      },
    },
  },
  {
    $sort: {
      delayRate: -1,
    },
  },
  {
    $limit: 20,
  },
]);
```

- Before (`.hint({ $natural: 1 })`): PROJECTION_SIMPLE > COLLSCAN; 5,819,079 docs examined; 14,428 ms server, 14,430 ms wall.
- After (default plan): PROJECTION_SIMPLE > COLLSCAN; index none; 0 keys and 5,819,079 docs examined; 5,815,932 returned by the query stage; 14,592 ms server, 14,594 ms wall.

Ranking every route must read every flight, so no index helps; this is why Phase 3 pre-aggregates into stats_route. Both plans read all 5,819,079 documents (PROJECTION_SIMPLE > COLLSCAN), so an index cannot help this query.
